# 模块与跨项目扩展契约

日期：2026-11-12，2026-11-17补页面贡献、能力投影与后端导入门禁。状态：设计规范；有限静态页面贡献已本地实现，其余扩展按下文区分。用于 Sun World 内部业务模块及未来其他项目的接入。[实现规范](dsh-implementation-standard.md)定义后端与运行时，[工程文件规范](../repository-conventions.md)定义命名、格式和测试位置。本文定义模块如何注册、鉴权与插入页面，不表示已有运行时插件市场。

具体项目落地见[Stars 首页与全项目接入方案](project-federation-plan.md)及[项目台账](../product/project-integration-inventory.md)。公开项目目录/外链只属于入口互通，不等于业务服务已启用第二项目；本文件的多项目数据迁移门槛适用于实际接受多项目业务数据的服务。

## 1. 扩展边界

模块是有明确 owner 的业务能力；插件是模块对外提供的一组注册声明与适配器。两者不要求独立服务。首期静态注册、构建时装配，禁止上传代码、远程脚本注入、任意 iframe 或运行时 npm 安装。

| 接入需求 | 采用方式 | 边界 |
| --- | --- | --- |
| 本仓库增加业务模块 | Web manifest + API manifest + 公共服务 | 同一部署，模块只能写自己拥有的数据 |
| 其他项目复用 UI 或契约 | 通过工作区包的稳定 exports；有真实消费者后再独立发包 | 不导出 Sun World 路由、账户 store、环境变量读取或数据库实现 |
| Sun World 调用外部项目 | `integrations` 下固定项目 adapter 调用版本化 API | 外部项目仍是资源授权与业务状态的权威；不跨项目直连数据库 |
| 外部项目调用 Sun World | 版本化 API/事件，项目服务身份与明确授权 | 不共享浏览器 Cookie，不让外部服务冒充 admin |
| 多项目共用一个部署 | 单独落实 ProjectContext、资源隔离、凭据及迁移后启用 | 本轮只定义契约；单项目原型不能宣称支持多租户 |

不立即抽出通用权限中心、插件市场、事件总线或共享数据库。保留适配接口；出现第二个真实消费者后再验证抽包价值与兼容要求。

## 2. 统一注册契约

平台组合根显式组装模块。后端声明业务能力与工具，前端声明组件、路由和页面贡献；二者通过 `module_id` 对应，不能让后端下发任意可执行 JS。

| 声明 | 含义 |
| --- | --- |
| module_id / version / owner | 稳定业务身份、版本和维护责任；与物理目录名分离 |
| dependencies | 依赖的公开模块接口及兼容版本；不得依赖私有文件路径 |
| capabilities | 后端登记的能力键、支持的资源类型与项目范围 |
| routes / navigation / contributions | Web 显式声明的页面、导航及扩展点贡献 |
| tools / skills | 后端权威工具契约和模块拥有的产品 Skill |
| data_owners / migrations | 数据所有权与兼容迁移；不允许前端插件声明即创建表 |
| configuration | 类型化非敏感配置；秘密只引用服务端 secret ref |

稳定标识由平台登记，不通过显示名称推导。业务 ID 沿用 `blog-content` 等已有决策；跨项目区分产品 app_id、目标 tenant_ref、下级 resource_scope 与资源 owner，不把目录 project_id 当数据租户。完整标识、登录/绑定、撤销与代办流程以[身份隔离规范](federated-identity-and-isolation.md)为准。能力 `blog.article.read_public` 在目标范围内独立授予。

模块停用不删除数据或历史。声明移除先停止准入、撤销运行、处理挂载组件和后台任务，再停止装配；破坏性迁移另行发布。新旧版本能否并存由契约明确，不使用“最新版本”隐式升级。

后端业务模块/core已接[静态导入门禁](../development/module-import-boundary.md)：跨业务直接引用须经过所属模块public及唯一静态公开值声明，registry由组合根注入，不由业务反向创建。旧适配层及间接依赖仍按迁移范围保留；此检查不授予能力，也不是Python运行时隔离。

## 3. 各模块鉴权矩阵

身份认证只回答主体是谁。授权输入至少是 `Principal + TargetContext + capability + ResourceRef + operation context`；角色是授予能力的方式，菜单可见性不是授权依据。平台默认拒绝未知能力、项目和资源类型。

| 模块 | 主体及能力范围 | 资源检查 / Agent 边界 |
| --- | --- | --- |
| 博客公开内容 | 匿名或登录主体；`blog.article.read_public` | 当前项目公开资源；P1 只读工具，无正文/已删除不返回 |
| 博客草稿（P2） | 登录作者；`blog.draft.read_own/write_own` | project 与 owner_user_id 均匹配；写入带版本；不因 author 展示名相同放行 |
| 博客发布（P2 独立门槛） | 具备 `blog.article.publish` 的登录用户 | 对目标草稿另有可读取/审核权限；确认绑定项目、主体、目标、摘要与版本 |
| AI 普通聊天 | 保留现有匿名配额及登录持久化 | 会话/Provider/persona/用户 Skill 按账户与项目归属；Agent 场景另行授权 |
| Agent 运行 | 登录、白名单、`agent.run.create` 与场景要求能力 | get/cancel 要求同项目同 owner；工具执行逐项重验，不继承全部用户权限 |
| 身份与授权管理 | 用户维护本人绑定；管理授权要求独立管理能力与近期认证 | 禁止给自己提升权限、越过可授予集合或删除最后恢复管理员 |
| 评论/运营 | 公开评论读取、审核/统计分别登记能力 | 不把内部审核内容与用户标识送入公开摘要工具；未来扩展独立验收 |
| 外部项目 integration | 项目服务身份；必要时叠加用户委托 | 本地策略和外部项目策略均通过；连接授权不等于用户可访问全部外部资源 |
| admin 管理界面 | 按具体业务能力显示入口 | 不单独拥有“可直接改任意表”的权力；后台也调用模块服务 |

表中新增能力均为设计名称，必须经 registry 登记后才能使用；不据此改变现有 admin 权限。网页按钮和工具列表可基于能力投影隐藏，但每次请求仍由 API 执行真实鉴权。行级操作能力由资源所属服务计算，不能仅靠全局 `canPublish` 标志决定所有文章均可发布。

跨项目的服务 token 至少约束 issuer、audience、project、scope、时效和撤销；首期若仅支持服务主体，就不提供用户代办。用户委托需单独绑定外部主体、目标项目与授权记录，不能信任请求中的 `user_id`、邮箱或显示名。Worker run 凭据仅用于内部运行，不能充当外部项目访问 token。

## 4. 页面插入的四种方式

现有 `AppModule` 支持 routes/nav/seo/preload。2026-11-17新增有限静态贡献：首个`ai.workspace.tools` v1只接现有公开博客问答入口，见[实际接口与验收](../development/page-contributions.md)。其他候选slot、写action及完整跨项目授权仍是设计，不应描述成已实现接口。

| 类型 | 注册位置 / owner | 适用内容 |
| --- | --- | --- |
| 完整页面 route | 模块 `index.ts` 暴露 AppModule，现有 registry 组装 | 博客详情、草稿工作台；路由级 lazy，应用布局负责 shell |
| 导航项 navigation | 模块声明，由 app/layout 集中渲染 | 菜单、导航分组；绑定 route ID、文案键和能力，不重复手写 URL |
| 页面区块 panel | 宿主声明 slot contract，模块声明 contribution | 首页卡片、详情辅助区、AI 工作区工具面板 |
| 操作 action | 宿主声明动作区及支持上下文，模块提供受控操作 | 编辑器“生成建议”、草稿“提交审核”；有 busy、失败、确认语义 |

宿主拥有布局、可见区域和传入上下文，贡献模块拥有组件与数据适配。应用组合根收集各模块的贡献，注入通用 registry；`shared` 不扫描或 import 业务模块，宿主不深入 import 插件内部组件。

首批扩展点（仅按实际页面需要创建；当前仅AI工作区的公开入口已实现）：

| slot ID | 宿主 | 最小上下文 | 约束 |
| --- | --- | --- | --- |
| `home.sidebar.cards` | home | 主题、语言、当前项目 | 可选卡片独立失败；移动端由宿主排序；ICP 保留为宿主固定内容 |
| `blog.detail.aside` | blog | article ID、公开版本（若有）、项目 | 不默认传整篇正文或私有作者资料；桌面/移动位置由宿主决定 |
| `blog.editor.actions` | blog | draft ID、expected version、项目、受控保存回调 | 写操作走模块服务；不能直接写编辑器 store 或绕过确认 |
| `ai.workspace.tools`（已本地实现v1） | ai | chat场景、sidebar/rail展示；独立scope及显示能力投影 | 当前只挂公开导航，不传聊天/正文；受限能力路径仅合成投影测试，不新增运行授权 |
| `manage.overview.panels` | admin | 项目及资源范围 | 服务端授权统计；未授权不拉取数据；单卡失败不破坏后台 |

贡献声明的后续设计示例（非当前接口的可直接调用代码；实际注册有显式项目列表、模块依赖与严格版本字符串，以上述开发说明为准）：

```ts
const blogQaContribution = {
  id: 'blog-content.qa-panel',
  moduleId: 'blog-content',
  slot: 'ai.workspace.tools',
  slotVersion: 1,
  order: 200,
  requires: ['agent.run.create', 'blog.article.read_public'],
  load: () => import('./ui/BlogQaPanel'),
}
```

`requires` 采用全部满足语义，若需要任一能力须另声明 `anyOf`，禁止模糊解释。slot 定义可接受的贡献类型、props schema、版本、最大数量及排序；同 order 以稳定 contribution ID 排序。未知 slot、重复 ID、依赖环或不兼容 slotVersion 在构建时拒绝，不静默显示错误组件。

运行时先检查模块启用、项目准入与能力投影，再 lazy 加载；每个贡献独立加载态、错误边界和重试。权限加载中或未知时不展示受限内容。模块关闭/账户或项目切换时卸载组件、取消请求并清理缓存；迟到响应必须校验原上下文，不得显示到新项目。

当前首个slot采用构建时静态代码，由应用组合根收集AppModule.contributions，shared不import业务模块。保留既有Web模块ID（blog/ai），不自动把它们映射成后端blog-content或授权身份。UI模块开关只控制贡献装配，不声称已停掉后端运行；真实模块停运仍遵守第2节的准入/撤销顺序。公开入口requires=[]用于发现页面，能力投影未知也可显示；受限声明要求全部能力满足才加载，实际API继续授权。本地已有[只读显示能力投影](../development/capability-projection.md)，复用当前会话、公开读与原管理员近期规则，仅覆盖当前十个登记能力；最多15秒的快照按账号/会话隔离，失败或过期移除受限贡献。显示结果不作为实际API凭据，不授予Agent运行或写入，也不能借普通聊天persona/Skill加载状态推导权限。首个view上下文没有受控写回调，不能直接拿来接编辑器写action。

组件通过类型化 props、回调和模块 API 通信；不操作外部 DOM、不监听无命名全局事件、不写其他模块 store。确有跨模块事件时由 app 声明版本化事件和生命周期，禁止任意字符串广播。CSS 使用 tokens 和作用域样式，不覆盖宿主通用选择器；键盘顺序、焦点恢复、空态和响应式由 slot 契约覆盖。

## 5. 跨项目身份、数据及契约演进

`ProjectContext` 只表示产品选择；完整 `TargetContext` 还包含目标的工作空间/商户/个人范围及资源层级，由目标服务根据已验证凭据和成员关系解析；浏览器只能提出项目选择，不能自行授权。单项目阶段由服务器注入唯一配置项目，拒绝其他项目选择，不接受任意 header 作为租户证明。此时可以暂不批量给旧表加 project_id，但禁止启用第二项目。

业务服务接受第二产品或第二工作空间/租户前必须完成下列隔离；即使只有一个产品，个人档案和会话仍须按用户隔离。仅添加公开项目外链不触发数据迁移。

验收清单：

1. 所有资源、关系查询、唯一键、幂等键、会话、run、来源、确认、outbox、审计与配额带适用的环境/产品/租户/主体范围；旧数据回填至明确项目，跨项目默认拒绝。
2. 缓存键、前端 query key、Worker 凭据、Provider/集成凭据选择均带项目上下文。私有数据不使用跨项目全局缓存；公开共享内容也必须显式声明共享策略。
3. 外部 adapter 把远端错误、分页、ID、版本和超时映射为稳定本地契约，保留远端 request ID；网络与重定向约束沿用平台出站政策。
4. 写请求的超时不等于远端未执行。远端支持幂等则传稳定请求键；不支持则标记 unknown、查询对账或人工确认，不能自动重复写。
5. 外部事件/Webhook 验证签名、时间窗和事件 ID，按项目去重，并处理重复、乱序、丢失与拉取对账。没有需求时不先搭消息总线。
6. 提供两个项目、相同本地资源 ID、不同用户及服务主体的隔离测试；权限、搜索、导出、日志、缓存、回调和撤销都不能串项目。

契约标明 API major、模块版本和 schema hash。兼容新增字段先验证旧消费者；删除/改义通过新 major 或明确退役周期，不要求所有项目同日升级。适配器的 consumer contract fixture 由调用方维护，提供方发布前验证；仓库内使用生成物可减少漂移，跨仓库仍需固定版本和兼容测试。

## 6. 模块交付清单

每个新模块的文档必须给出：ID/owner、公开入口与依赖、文件/测试目录、数据所有权、能力及资源策略、路由/贡献清单、失败隔离、跨项目范围、版本兼容、开关与退役行为。测试至少包含拒绝路径、宿主卸载、项目切换、未知 slot/schema、直接调用 API 越权，以及外部连接超时/重复写结果不明。

首期不要求模块具备全部入口：纯 API 模块无需伪造页面，纯展示模块无需创建数据库，工具模块也不自动生成管理页面。只声明真正拥有的能力。
